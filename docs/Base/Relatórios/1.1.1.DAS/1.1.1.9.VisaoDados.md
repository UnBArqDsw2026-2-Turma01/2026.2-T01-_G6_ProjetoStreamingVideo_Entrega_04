# 1.1.1.9. Visão de Dados

> **Responsável:** Daniel de Oliveira Lira · **Revisão cruzada:** SubEquipe_01 · **Issue:** [#9](https://github.com/UnBArqDsw2026-2-Turma01/2026.2-T01-_G6_ProjetoStreamingVideo_Entrega_04/issues/9) · **Status:**  🟢 Concluído

## Conteúdo

### Escopo e justificativa

No modelo de Documento de Arquitetura de Software adotado (UFRN/DCA, derivado do SAD do RUP), a **Visão de Dados** é uma seção opcional voltada à descrição dos dados persistentes do sistema, em especial o mapeamento entre os objetos do domínio e um banco de dados (normalmente relacional), representado por diagramas de classes voltados a persistência ou por um Modelo de Entidade e Relacionamento (MER).

Nesta entrega, a Visão de Dados fica **fora do escopo** de modelagem porque o sistema integrado no [repositório de código](https://github.com/UnBArqDsw2026-2-Turma01/2026.2-T01-_G6_ProjetoStreamingVideo_Entrega_04_Codigo) **não possui banco de dados nem camada de persistência em disco**. Todo o estado necessário para executar o cenário arquitetural **CA-01 — Live com doação destacada** é mantido exclusivamente em memória durante o ciclo de vida do processo Node.js.

| Contexto | Estruturas mantidas em memória (sem SGBD) | Origem da decisão |
| --- | --- | --- |
| `identidade` | Sessões ativas, credenciais e fatores de verificação (TOTP) | E03 (SubEquipe_03) |
| `transmissao` | Configurações de live (`StreamConfig`), lives ativas e vínculo `live → criador` | E03 (SubEquipe_01 e SubEquipe_03) |
| `conteudo` | Registros de VOD gerados após o encerramento da live | E03 (SubEquipe_01) |
| `monetizacao` | Carteiras de moeda virtual, histórico de recargas (`CheckoutPendente` / `Recibo`) e comprovantes de doação/repasse | E03 (SubEquipe_02) |
| `chat` | Salas de chat ativas por live e lista de ouvintes inscritos | E03 (SubEquipe_03) |
| `moderacao` | Regras de filtragem do AutoMod e vereditos das mensagens | E03 (SubEquipe_03) |

Desenhar um MER ou um esquema relacional para tabelas que não existem no código violaria o princípio adotado pelo grupo no [planejamento](../../../Projeto/Planejamento.md) e na [Introdução](1.1.1.1.Introducao.md): o DAS descreve a arquitetura efetivamente implementada e verificável, evitando modelagem especulativa desconectada do artefato executável. A estrutura das entidades e DTOs trafegados entre os contextos já está documentada nos contratos do `@g6/shared-kernel` e nas visões Lógica e de Implementação.

## O que mudou desde a E02/E03 e por quê

| Antes | Agora | Por quê |
| --- | --- | --- |
| E02: modelagem conceitual de domínio (diagramas de classes sem amarração a SGBD) | Entidades representadas como tipos, interfaces e estruturas em memória no monorepo | O foco da E04 é integrar os módulos da E03 no CA-01 sem introduzir infraestrutura de banco de dados |
| E03: cada subequipe mantinha seus próprios repositórios em memória isolados | Estado em memória continua isolado por contexto, mas a troca de dados entre contextos ocorre via DTOs e IDs com marca de tipo no `@g6/shared-kernel` | Evita acoplamento direto entre estruturas internas de pacotes diferentes (ex.: `monetizacao` consulta o criador da live via `TransmissaoPort.consultar`, sem acessar o estado interno de `transmissao`) |
| E04 (organização inicial): Visão de Dados prevista como seção completa pelos quatro integrantes da SubEquipe_02 | Seção mantida apenas como justificativa formal de escopo (opcional no modelo) | Confirmado que não há banco de dados no projeto e que a seção no template é opcional quando não existe persistência |

## Decisões e senso crítico

- **Alternativa descartada: introduzir SQLite ou PostgreSQL para justificar a Visão de Dados.** Adicionar um banco de dados relacional apenas para produzir um MER foi descartado no [planejamento](../../../Projeto/Planejamento.md) (*“Evitar: banco real”*). O esforço desviaria o foco da integração arquitetural do CA-01 e exigiria reescrever repositórios das três subequipes em prazo curto.
- **Limitação assumida: volatilidade e ausência de transações distribuídas.** Como todos os dados residem na memória RAM do processo, reiniciar o servidor descarta sessões, saldos de carteira, lives e histórico de chat. Além disso, não há garantias ACID em disco nem controle de concorrência entre múltiplos processos.
- **Mitigação para evolução futura.** Como os contextos já se comunicam exclusivamente por *ports* e interfaces de repositório internas, a introdução futura de persistência (por exemplo, um banco relacional para `monetizacao` e `identidade`) exigiria apenas novas implementações de adaptadores de repositório, sem alterar o contrato do `@g6/shared-kernel`.
